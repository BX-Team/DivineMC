# DivineMC

A Minecraft server: a fork of [Purpur](https://github.com/PurpurMC/Purpur) (itself a fork of Paper) focused on performance and multithreading. Java 25, Gradle, [paperweight](https://github.com/PaperMC/paperweight) patcher. One branch per Minecraft version (`ver/<mc>`); the newest one is where development happens.

## Architecture

Only DivineMC's own sources and the exported `.patch` files are tracked. Everything upstream is generated by `applyAllPatches` into gitignored directories, each a separate git repository whose history **is** the patches.

| Tracked | Applies to (gitignored repo) | Holds |
| ------- | ---------------------------- | ----- |
| `divinemc-server/src/main/java` | — | DivineMC's own server code (`org.bxteam.divinemc.*`, ported third-party code). |
| `divinemc-server/src/c` | — | Native math (from C2ME); prebuilt libraries are in `src/main/resources`. |
| `divinemc-server/minecraft-patches` | `divinemc-server/src/minecraft/java` (and `.../resources`) | `sources`/`resources`: per-file patches; `features`: feature patches. |
| `divinemc-server/paper-patches` | `paper-server` | `files` and `features`. |
| `divinemc-server/purpur-patches` | `purpur-server` | `files` and `features`. |
| `divinemc-api/src/main/java` | — | DivineMC's own API classes. |
| `divinemc-api/paper-patches` | `paper-api` | `files` and `features`. |
| `*/build.gradle.kts.patch` | `*/build.gradle.kts` | Single-file patches over Purpur's build scripts (dependencies live here). |
| `build-data/divinemc.at` | — | Access transformers, applied on setup. |
| `patches/removed/<mc>` | — | Dropped patches, kept for reference only. |

- Each applied repo is: upstream base → one `divinemc File Patches` commit (tag `file`) → one commit per feature patch. `base` tags the commit below the file patches.
- A feature patch is a large, optional change that can be dropped during a Minecraft update; anything small goes into the per-file patches.
- Configuration is `org.bxteam.divinemc.config.DivineConfig` (global, one static nested class per category) and `DivineWorldConfig` (per world, `level.divineConfig`).
- `gradle.properties` holds `mcVersion` and `purpurRef`, the upstream commit everything is applied on.

## Commands

```bash
./gradlew applyAllPatches                           # generate the applied repos from the .patch files
./gradlew :divinemc-server:rebuildAllServerPatches  # export the applied server repos back to .patch files
./gradlew rebuildPurpurPatches                      # same for paper-api, purpur-api and the build.gradle.kts patches
./gradlew :divinemc-server:compileJava
./gradlew :divinemc-server:test                     # about a minute
./gradlew build                                     # what CI runs: compile, tests and checkstyle
./gradlew createPaperclipJar                        # the server jar
```

Run the two rebuild tasks as separate Gradle invocations; together they fail task validation.

The user starts the server (`runDevServer`) and runs benchmarks themselves.

## Working with Patches

Never edit a `.patch` file, its number or its order by hand: change the applied repo and rebuild.

- **`applyAllPatches` hard-resets the applied repos.** Anything there that isn't exported to `.patch` files is lost, so rebuild before applying and before switching branches. A lost state is still in that repo's `git reflog`.
- **Per-file patch**: edit the source, `git commit -a --fixup file` in that repo, `git rebase -i --autosquash base`, then rebuild. `fixup<Project>FilePatches` does the first two steps when nothing conflicts.
- **Existing feature patch**: find its commit with `git blame`/`git log`, `git commit -a --fixup <hash>`, `GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash <hash>^`, then rebuild. A new commit on top would export as a separate patch instead.
- **New feature patch**: commit in the applied repo with the patch title as the subject, then rebuild.
- A rebuild right after a rebuild must change nothing. When a change only moves code between patches, `git write-tree` must be the same before and after.
- `build.gradle.kts` changes: edit the applied `divinemc-*/build.gradle.kts`, then `rebuildPurpurSingleFilePatches`.
- A new access transformer is a line in `build-data/divinemc.at`; it takes effect on the next `applyAllPatches`.
- Checkstyle skips our own sources per directory, not recursively: a new package needs its own line in `paper-api/.checkstyle/ignored_directories.txt` (API) or `paper-server/.checkstyle/ignored_directories.txt` (server), both kept as per-file patches. A new API package also needs a `package-info.java` with `@NullMarked`, or the API tests fail.

### Updating upstream

1. Set `purpurRef` in `gradle.properties` and run `./gradlew applyAllPatches`.
2. It stops at the first patch set that fails, in this order: `build.gradle.kts` patches, API, Minecraft, then `paper-server`/`purpur-server`. Fix the failure in the applied repo (`git am --continue` through the feature patches), rebuild that patch set, and run the apply again. Once the Minecraft patches are done, continue with `:divinemc-server:applyServerPatches`, which leaves them alone.
3. When a conflict is upstream changing the code a patch touches, keep upstream's new behaviour and re-apply ours on top; don't restore the old lines.
4. `./gradlew build`, then `applyAllPatches` once more to prove the exported patches reproduce the tree, then stage everything and run `scripts/upstreamCommit.sh <old purpurRef>`, which writes the commit.

When upstream starts doing what one of our patches does, drop ours and move the patch to `patches/removed/<mc>`.

## Working on Tasks

- If the message is a question, investigate and answer only. Edit files only when asked to fix or implement.
- Stay within the scope of the request. Mention related problems you notice instead of fixing them.
- Fix the cause, not the symptom. No special-case constants or hardcoded lists to make one case work.
- Don't claim a performance gain without a measurement; say what the change is expected to do and what was measured separately.
- When a change can't be verified without running the server, say so.
- Trust the user's reports about what they observed on a running server.
- Features are ported between version branches by switching branches in this checkout, never through extra worktrees.
- Commit in the root repository only when asked, and never push.
- Don't edit `CLAUDE.md` or `AGENTS.md` unless asked. Decisions, plans and progress don't belong in them.

## Code Guidelines

### Changes to upstream files

- Every change in a Minecraft, Paper or Purpur file is marked: `// DivineMC - <reason>` at the end of a changed line, `// DivineMC start - <reason>` … `// DivineMC end - <reason>` around a block. Use the patch's title as the reason.
- Make the smallest diff: no reformatting, no reordering, no cleanup of surrounding upstream code. Put the logic in a class under `divinemc-server/src/main/java` and leave a one-line hook in the upstream file.
- No new imports in upstream files — use the fully qualified name. No `var`.
- Config values are read as `org.bxteam.divinemc.config.DivineConfig.<Category>.<field>`. A new option is a public field plus its `getX(...)` call in the category's `load()`; prefer `DivineWorldConfig` when the value can differ per world.
- New classes are `@NullMarked` (jspecify) with explicit `@Nullable`; upstream classes keep the annotations they already use.

### Behaviour

- Vanilla and Paper API behaviour, plugin compatibility and on-disk formats stay intact unless the change is the point of the task; an optimization that changes behaviour sits behind an option that is off by default.
- An API change is two changes: the API source and its server implementation.
- On hot paths: no allocation, boxing, streams or capturing lambdas where the surrounding code uses plain loops; keep early exits and fast paths.
- Before moving work to another thread or loosening a thread check, account for every piece of mutable state it touches, the chunk and entity lifecycle, shutdown, and what plugins can reach through the API. Parallel world ticking and regionized chunk ticking make "main thread" mean several threads.

### Comments

- NO file-header banners and NO divider comments.
- Apart from the `// DivineMC` markers, avoid inline comments. Add one only where the code is genuinely non-obvious: a footgun, a race, a reason a thing is done backwards. One line, two at most.
- Keep upstream comments, and the credit to the original project in code ported from one.

### Testing

Tests live in `divinemc-server/src/test/java`. One test per real trap, not one per function; an optimization that must match vanilla gets a parity test against the vanilla path.

## Bash Guidelines

- Don't pipe output through `head`/`tail`/`less` to truncate — use tool-native flags (`git log -n 10`, `./gradlew -q`). Read the full output.
- `grep` on this machine is `ugrep`: give it a single root directory.
- Don't create scratch files (scripts, notes) unless asked.
- When given failures, just fix them — don't argue about who introduced them.
